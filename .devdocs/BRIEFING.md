- **Phase:** Phase 64 (**cursor offset fixed, review triaged, doc standard cleaned — awaiting user build**). The cursor bug was a coordinate-space error, not a cursor error: `surface_at()` in `src/xdg_view.c` passed **window-geometry-local** coordinates to `wlr_xdg_surface_surface_at()`, which takes **wl_surface-local** ones. They differ by `xdg_surface->geometry.x/y`, the CSD margin, non-zero for essentially every GTK client — so every hit test landed that far up and to the left of the real pointer. Rendering was never wrong (`wlr_scene_xdg_surface_create()` applies the same correction with the opposite sign), which is exactly what disguised it as a cursor problem. Also normalised 17 `##`-prefixed comments matching no `AGENTS.md` prefix. Full detail: DECISIONS_LOG Phase 64.

- **Phase:** Phase 62 (**SECOND ROOT CAUSE FOUND AND FIXED — awaiting user build**). With Phase 61's NULL-deref fix installed, the user confirmed VT switching survives and Firefox is fine — but **pavucontrol crashed the compositor immediately**, producing a second core dump (`hikari.52741.1001.core`, signal 6). This is a completely separate defect from Phase 61. `xdg_popup_create()` called `popup_unconstrain()` at popup-creation time; `wlr_xdg_popup_unconstrain_from_box()` ends with `wlr_xdg_surface_schedule_configure()` (`wlr_xdg_popup.c:534`), which asserts `surface->initialized` (`wlr_xdg_surface.c:168`) — and wlroots emits `new_popup` straight from the client's `get_popup` request, **before the popup surface has ever been committed**. So hikari aborted on **every xdg_popup ever created**: every GTK menu, combo box, dropdown and tooltip. Deterministic, not a race. **This retires the "lots of children/background processes" theory entirely** — the real predictor is *native-Wayland clients that open popups*. Firefox under XWayland never creates an xdg_popup (survives); pavucontrol opens one on launch (dies instantly). Fixed in both `src/xdg_view.c` and `src/layer_shell.c` by deferring the unconstrain into the popup's existing `initial_commit` branch. Notably, **hikari already understood this exact wlroots 0.20 constraint for toplevels** — `hikari_xdg_view_init` carries a comment citing `wlr_xdg_surface.c` line 168 as the reason `wlr_xdg_surface_ping` was removed — but never applied it to popups, in either file. Full trace: DECISIONS_LOG Phase 62.

- **Phase:** Phase 61 (**CRASH ROOT-CAUSED AND FIXED — awaiting user build**). The compositor crash is a **NULL pointer dereference in hikari's own `session_active_handler`**, proven by the first core dump ever captured in this project. `session_active_handler()` read `*(bool *)data`, but wlroots emits `session->events.active` with `data == NULL` (`backend/session/session.c:27`, `:33`). That is an unconditional segfault on **every** VT switch and every seat disable — 100% deterministic, not a race and not memory corruption. `gdb bt` on `/var/coredumps/hikari.27920.1001.core` puts frame #0 at `session_active_handler+10`, the first memory access after the prologue, reached libseat -> wlroots -> `wl_signal_emit_mutable`. Fixed by reading `server->session->active` instead. **Two prior conclusions are corrected:** (1) there were always *two* crash signatures — `/var/log/messages` shows SIGSEGV (11) at 13:59:15, 14:26:15 and 14:51:15 alongside the SIGABRTs, so the "SIGABRT, not SIGSEGV" premise that drove Phases 53-57 was half wrong; (2) the captured crash printed **no assertion message** and exited 139, so Phase 57's prediction of a wlroots assertion did not hold for this fault. Why it looked app-triggered: the user runs hikari from a TTY while `Xorg :2` holds VT `v1`, so anything pulling the VT back disabled hikari's seat and killed it ~15s in. Full trace: DECISIONS_LOG Phase 61.

- **Phase 57** (**ROOT CAUSE FOUND AND FIXED — awaiting user build**). The window-close crash is a wlroots-side assertion, not a hikari memory bug. `src/xdg_view.c` registered `request_fullscreen` on the **xdg_toplevel** but removed it in `destroy_handler`, which is bound to the **xdg_surface**. wlroots 0.20 destroys the toplevel role object *before* emitting the xdg_surface destroy signal, and `destroy_xdg_toplevel()` asserts every toplevel signal has no listeners left — so wlroots `abort()`ed (SIGABRT) on every window close, three lines before hikari's cleanup ran. Fixed by adding a `toplevel_destroy` listener on `xdg_toplevel->events.destroy` that releases the toplevel-scoped listener (and itself) at the right moment. **Two corrections to earlier phases:** (1) Phase 53 concluded the binary was a `DEBUG=YES` build with hikari assertions live — wrong; it is a release `-DNDEBUG` build with hikari's assertions compiled out, and the aborting assertion was inside `libwlroots-0.20.so`, which *is* built with assertions on. (2) The Phase 56 visibility refactor **was present in the binary that crashed at 13:46:57** — it fixed a real separate latent defect class but was never the cause of this crash. Full trace: DECISIONS_LOG Phase 57.

- **Phase 55** (Root-Cause Architecture Analysis + Single-Writer Visibility Refactor) — analysis and plan; superseded by Phase 56's execution. Answers the question "is the architecture itself causing the crashes": **yes, and the flaw is nameable** — the fact *"this view is visible"* is stored in **six** independent representations (hidden flag, `workspace->views`, `hikari_server.visible_views`, `group->visible_views`, the `group->visible_server_groups` aggregate, and the scene-node enabled bit) with **no single writer**. Entry is split across two functions callers must remember to pair; exit is one function; `hikari_view_lower()` hand-writes the whole linkage a third time. Group lifetime then depends on an unwritten, unasserted invariant linking two of those representations — and `hikari_view_unmap()` contains a branch that sets the hidden *flag* without performing the *transition*, then frees the group, producing a simultaneous three-list + freed-group use-after-free. That is exactly the delayed-corruption signature behind the long history of "random" crashes and the current SIGABRT-with-no-core. Remediation is a bounded refactor — **Single-Writer Visibility Transitions** — confined mostly to `src/view.c`, ~18 call sites, fully wired function-by-function in `PLANS.md` item -6. Explicitly **not** the Phase 44 DOD/SoA rewrite (that rejection stands; allocation strategy is unchanged). Honest caveat: this removes a defect *class* plus one specific identified UAF path, but has not been proven to be the exact live crash, because no crash output or core has been captured yet — Step 4 (headless smoke test under `MALLOC_CONF=junk:true`) closes that gap and should be built first.
